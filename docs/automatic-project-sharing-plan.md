# LanDevLink 多服务项目自动分享实施计划

状态：阶段 0 至 2 与阶段 3 的基础提示已实现；阶段 4 待真实使用数据决定
日期：2026-11-06

实施记录：已加入启动时首页及最多 8 个同源资源扫描、会话级关联服务允许列表、保留路径、有限文本响应转换、密码与过期检查、兼容警告和 AI 修复指令。双服务集成检查位于 `tests/LanDevLink.IntegrationChecks`。发布构建默认关闭自动兼容，可设置 `LANDEVLINK_AUTO_SHARE=1` 启用。动态拼接、Worker、Service Worker、iframe 与严格 CSP 仍属已知限制；阶段 3 的详细来源诊断和实际设备验收尚未完成。

## 1. 背景

LanDevLink 当前以单个本机地址作为分享目标，例如 `http://localhost:5173`。这种方式适用于所有浏览器请求都进入同一个开发服务的项目。

部分前后端分离项目会在浏览器代码中直接访问其他本机地址，例如：

```text
前端页面：http://localhost:5173
后端接口：http://localhost:8080/users
```

分享后，访问者浏览器中的 `localhost:8080` 指向访问者自己的电脑，请求会失败或等待超时，表现为页面切换慢、接口无响应或部分资源无法加载。

目标用户主要使用 vibe coding，不应要求他们理解前端、后端、API 前缀、路径转换或代理规则。因此，本次调整不在界面增加技术配置，而是把兼容逻辑收进分享模块内部。

## 2. 产品决定

将产品模型从“分享一个端口”调整为“分享一个项目会话”。

用户仍然只需要：

1. 选择检测到的项目。
2. 点击“开始分享”。
3. 复制链接或二维码。

LanDevLink 自动完成：

- 分享主页面服务。
- 识别页面内容实际引用的其他本机 HTTP、HTTPS、WebSocket 服务。
- 为识别到的关联服务建立当前会话内的代理映射。
- 将可安全转换的本机地址替换为分享地址下的内部路径。
- 无法安全转换时给出非技术化提示和可复制的 AI 修复指令。

用户界面不出现“后端地址”“API 前缀”“移除前缀”等设置。

## 3. 目标与非目标

### 3.1 目标

- 单击即可分享常见的前后端分离开发项目。
- 支持页面中写死的 `localhost`、`127.0.0.1` 和 `::1` 服务地址。
- 保持现有密码、有效期、停止分享和访问设备统计能力。
- 关联服务只能在当前分享会话中访问。
- 失败时说明问题，不让访问者长时间等待超时。
- 所有复杂逻辑集中在分享模块，ViewModel 只消费分享结果和状态。

### 3.2 非目标

- 不代理公网服务。公网资源继续由访问者浏览器直接访问。
- 不开放任意端口或把 LanDevLink 变成通用局域网代理。
- 不自动修改用户项目源码。
- 不实现远程桌面、云浏览器或视频流式预览。
- 不在首版覆盖所有 Worker、Service Worker、iframe、CSP 和动态拼接地址。
- 不提供任意数量的手工路由配置。

## 4. 用户体验

### 4.1 正常流程

```text
正在检查项目……
已识别项目页面
已自动连接 1 个关联服务
分享已就绪
```

没有关联服务时保持当前流程，不增加额外信息。

### 4.2 部分兼容

发现无法自动转换的地址时，分享可以继续，但界面显示：

```text
项目可能有部分内容无法在其他设备加载
[复制给 AI 修复]
```

默认折叠技术详情。展开后可以显示地址类型和来源文件，但不要求用户做路由选择。

### 4.3 无法安全分享

如果检测到的关联目标不属于本机回环地址、目标不是可识别的开发服务，或者会扩大本机服务暴露范围，则不自动代理，并显示：

```text
检测到无法安全共享的项目服务
请使用“复制给 AI 修复”调整项目后重试
```

## 5. 目标架构

```text
访问者浏览器
    |
    | 分享地址
    v
ShareServer
    |-- 普通路径 -----------------> 主页面服务 localhost:5173
    |
    `-- /__landevlink/s/{id}/... -> 会话允许的关联服务 localhost:8080
```

`/__landevlink/` 是内部保留路径，不能由目标项目覆盖。`{id}` 使用当前会话生成的不透明标识，不直接暴露目标端口。

### 5.1 分享模块接口

保持 ViewModel 的调用面尽量小。建议让 `ShareServer.StartAsync` 返回启动结果，而不是让调用方理解路由和关联服务：

```csharp
public sealed record ShareStartResult(
    Uri ShareUrl,
    DateTimeOffset? ExpiresAt,
    int RelatedServiceCount,
    bool HasCompatibilityWarning);
```

密码、有效期和目标地址参数暂时保持现有形式，避免无必要地引入新的请求类型。

### 5.2 会话允许列表

每次分享维护独立映射：

```text
不透明服务 ID -> 已验证的本机目标 Origin
```

加入允许列表必须同时满足：

- 协议为 HTTP、HTTPS、WS 或 WSS。
- 主机为 `localhost`、`127.0.0.1` 或 `::1`。
- 地址由主页面或其文本响应实际引用。
- 服务可以在短超时内建立连接。
- 关联服务数量不超过固定安全上限。

分享停止或过期时清空整个映射。

### 5.3 文本响应转换

首版只处理可识别的文本内容：

- `text/html`
- JavaScript
- CSS
- JSON
- Web App Manifest

示例：

```text
原始：http://localhost:8080/users
替换：http://分享地址/__landevlink/s/{id}/users
```

WebSocket 示例：

```text
原始：ws://localhost:8080/socket
替换：ws://分享地址/__landevlink/s/{id}/socket
```

转换后需要移除或重新生成会失效的响应头，包括 `Content-Length`、`ETag` 和内容校验头。二进制、流式响应、SSE 和 WebSocket 数据不进行正文转换。

### 5.4 关联服务代理

内部代理收到保留路径请求后：

1. 验证当前访问密码 Cookie 和分享有效期。
2. 使用服务 ID 查询当前会话允许列表。
3. 移除内部保留路径。
4. 将剩余路径、查询参数、请求方法和请求体转发到关联服务。
5. 转换指向回环地址的 `Location` 响应头。
6. 对 `Domain=localhost` 等无法在分享地址使用的 Cookie 做受限处理。

未知服务 ID、过期会话和不在允许列表中的目标一律返回 404，不尝试动态连接端口。

### 5.5 运行时兼容脚本

首版不默认注入脚本。先通过文本响应转换覆盖常见的字面量地址，包括 HTML 资源、CSS、JavaScript 配置和普通接口基地址。

只有实际测试证明大量项目使用运行时动态拼接地址时，再增加一个受控的客户端适配器，用于处理：

- `fetch`
- `XMLHttpRequest`
- `WebSocket`
- `EventSource`

该适配器不能扩大服务允许列表，只能使用服务器已经识别并授权的映射。

## 6. 安全要求

以下要求不能为了自动化而省略：

- 绝不根据访问者提交的端口直接建立代理。
- 绝不自动代理所有正在监听的本机端口。
- 关联目标必须经过与主目标同等级别的回环地址验证。
- 所有内部代理路径必须经过现有密码、有效期和停止分享检查。
- 内部路径不能绕过随机分享入口获得访问权限。
- 限制关联服务数量、响应转换大小和检测超时。
- 日志不得记录密码、Cookie、Authorization 和完整敏感查询参数。
- 发现无法确认的地址时选择不代理，并生成修复提示。

## 7. 性能要求

- 二进制、视频、文件下载和流式响应保持流式转发。
- 仅缓冲需要检查的文本响应，并设置固定大小上限。
- 超过上限时停止转换、直接转发并记录兼容性警告。
- 不为每个请求重新探测已验证的关联服务。
- 同一个 Origin 在当前会话中复用同一个服务 ID。
- 保留 YARP 的连接池和 WebSocket 转发能力。

## 8. 代码调整范围

| 位置 | 调整内容 |
|---|---|
| `Services/ShareServer.cs` | 管理项目会话、内部路由、允许列表、响应转换和启动结果 |
| `Services/TargetUrlValidator.cs` | 提取可复用的回环目标验证，供主目标和关联目标共同使用 |
| `Services/LocalServiceScanner.cs` | 保留发现入口职责；补充 HTTP 服务识别，不再把“端口开放”等同于“可分享项目” |
| `ViewModels/MainViewModel.cs` | 展示检查状态、关联服务数量和兼容性警告 |
| `MainWindow.xaml` | 增加简短状态和“复制给 AI 修复”命令，不增加技术配置表单 |
| `README.md` | 更新支持范围、安全说明和已知限制 |
| 新测试项目 | 覆盖自动发现、地址转换、内部代理、安全拒绝和现有单服务回归 |

不新增通用路由配置模块；当前只有一个实现，复杂度应留在 `ShareServer` 内部，直到代码规模证明需要拆分。

## 9. 分阶段实施

### 阶段 0：建立可重复测试

- 创建最小测试项目。
- 启动临时前端和后端 Kestrel 服务，使用系统分配端口。
- 前端返回包含回环后端地址的 HTML、JavaScript、CSS 和 JSON。
- 后端提供普通接口、重定向、Cookie 和 WebSocket 测试端点。
- 证明当前实现无法让远端式请求正确进入后端。

完成标准：一条自动化测试能够稳定复现“页面引用其他 localhost 服务”的问题。

### 阶段 1：项目会话和安全映射

- 增加当前分享会话的关联服务允许列表。
- 增加内部保留路径和不透明服务 ID。
- 关联目标复用回环验证和可达性检查。
- 未识别端口、伪造服务 ID 和过期会话必须被拒绝。

完成标准：测试可以通过内部路径访问已授权后端，但不能访问任意本机端口。

### 阶段 2：静态自动兼容 MVP

- 检查有限大小的文本响应。
- 识别 HTTP、HTTPS、WS、WSS 回环 Origin。
- 为识别到的 Origin 建立映射并替换地址。
- 转换必要的重定向和 Cookie。
- ViewModel 显示“已自动连接 N 个关联服务”。

完成标准：用户不做配置即可访问典型的前端加后端测试项目。

### 阶段 3：兼容性诊断和 AI 修复提示

- 检测未能转换的回环地址、超大响应和不支持的加载方式。
- 生成不包含项目敏感内容的修复指令。
- 增加“复制给 AI 修复”按钮。
- 记录本次会话的兼容模式和失败原因，不持久化访问数据。

完成标准：无法自动处理时，用户能得到一个明确动作，不再只看到页面超时。

### 阶段 4：按证据增加运行时适配

只有阶段 2、3 的真实使用数据表明动态地址是主要失败原因时才实施：

- 注入外部兼容脚本，不使用内联脚本。
- 仅改写已授权目标。
- 覆盖 fetch、XHR、WebSocket 和 EventSource。
- 检查 CSP、Worker 和 Service Worker 兼容性。

没有数据证明需要时跳过该阶段。

## 10. 测试清单

### 10.1 正常行为

- 单服务项目行为与当前版本一致。
- HTML 中的回环接口地址被转换。
- JavaScript、CSS 和 JSON 中的回环地址被转换。
- HTTP 方法、请求体、查询参数和响应状态保持不变。
- WebSocket 可以通过内部路径建立连接。
- 分享密码和有效期同时作用于主服务和关联服务。

### 10.2 安全行为

- 公网地址不加入允许列表。
- 未被页面引用的本机端口不能访问。
- 访问者不能通过修改内部路径选择任意端口。
- 停止分享后所有关联服务立即不可访问。
- 新分享会话不能复用旧会话的服务 ID。
- 超过数量、大小或超时限制时安全失败。

### 10.3 兼容与性能

- gzip 或 Brotli 响应不会产生损坏内容。
- 大型文件不进入文本缓冲流程。
- SSE、文件下载和视频保持流式转发。
- 不含回环地址的页面不会出现可观察的明显性能退化。
- 多个访问者同时访问不会相互污染 Cookie 或服务映射。

## 11. 验收标准

发布前必须满足：

- 用户只填写或选择一个项目地址即可开始分享。
- 测试项目中，前端页面和独立后端接口均可从另一台设备访问。
- 页面切换不再因为访问者自己的 `localhost` 请求而等待超时。
- UI 不出现 API 前缀、路径转换和端口映射配置。
- 任意未授权本机端口无法通过分享入口访问。
- 当前单服务、密码、过期、停止分享和 WebSocket 行为没有回归。
- 无法兼容的项目得到明确提示和 AI 修复指令。

## 12. 发布与回滚

- 自动兼容能力使用一个内部功能开关，默认先在开发构建启用。
- 首次发布只启用阶段 1 和阶段 2 已通过测试的内容类型。
- 出现内容损坏或性能问题时，可以关闭响应转换，回退到当前单服务代理。
- 回滚不能影响密码、有效期和停止分享能力。
- 发布说明明确列出首版暂不支持的动态地址、Worker 和严格 CSP 场景。

## 13. 实施顺序摘要

1. 先建立双服务失败测试。
2. 增加会话级允许列表和内部代理路径。
3. 实现有限文本响应转换。
4. 接入非技术化状态提示。
5. 增加 AI 修复指令作为失败退路。
6. 根据真实失败数据决定是否实现运行时兼容脚本。

该顺序优先解决最常见问题，同时避免首版直接承担远程浏览器或通用内容重写系统的复杂度。
